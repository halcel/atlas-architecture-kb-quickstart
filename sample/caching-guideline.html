Guideline: Caching in customer-facing services

Status: Active · Owner: Platform Architecture · Last reviewed: 2026-09-15

Purpose

Customer-facing services (app backend, web shop, e-receipt) must stay fast during peaks without each team inventing its own caching. This guideline defines when to cache, where, and how to invalidate.

Two-tier caching

Use a small, bounded in-process cache (L1) for hot, rarely changing data such as store master data and feature flags. Size it by entry count, not by "whatever fits": a pod must never grow beyond its memory request because of cache growth.

Use a shared cache (L2) for data that is expensive to compute and shared across pods, for example precomputed rankings or personalised content. MongoDB Atlas is the approved L2 when the cached data is also queried by attributes; a pure key-value store is acceptable only for opaque blobs.

Invalidation

  • Prefer event-based invalidation (message queue or change streams) over short TTLs.
  • Every cache entry needs a TTL as a safety net; use a TTL index for L2 entries in MongoDB.
  • Never cache user-specific data in L1: it grows with the number of users and causes out-of-memory restarts.

Sizing and load tests

Before go-live, run a load test at 2x the expected peak and record cache hit rate, pod memory and L2 latency. Share the results with the platform team for cluster sizing. Target an L1 hit rate above 80% and L2 p95 latency below 10 ms.

Anti-patterns

  • Unbounded in-memory maps keyed by user or session.
  • Sticky sessions as a substitute for a shared cache.
  • Running two databases for the same data "because the reference architecture does".
